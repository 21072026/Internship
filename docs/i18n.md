# i18n — the translator pipeline and adding a locale (#2082)

The product ships in **EN / TR / DE**, free on every plan. All UI and mail copy
lives in one typed module, [`src/i18n/dictionaries.ts`](../src/i18n/dictionaries.ts)
(`const en = {…}`, `const tr: Dict = {…}`, `const de: Dict = {…}`). The type
`Dict = typeof en` is what makes a missing key a compile error. Keep it a single
TypeScript module; this pipeline exists so a translator never has to open it.

## The round trip

```bash
npm run i18n:export                    # i18n/exports/<locale>.json for every non-English locale
npm run i18n:export -- --locale de     # one locale
# … hand de.json to the translator, receive it back …
npm run i18n:import -- i18n/exports/de.json --check   # what would change; writes nothing
npm run i18n:import -- i18n/exports/de.json           # rewrite the changed literals in place
npm run check:i18n && npx tsc --noEmit
```

`i18n/exports/` is gitignored. The files are hand-off artefacts, not sources.

### What the translator receives

The file is plain JSON, one entry per string, in dictionary order:

```json
{
  "meta": { "format": "interncrm-i18n/1", "locale": "de", "sourceLocale": "en", "strings": 10836, "missing": 0, "howTo": "…" },
  "strings": {
    "nav.dashboard": { "source": "Dashboard", "target": "Übersicht" },
    "notifications.events[\"security.newDevice\"]": { "source": "New sign-in … {device} …", "target": "…", "note": "comment above the key in the source" }
  }
}
```

- **The key is the address.** Dotted path; array items by index (`calendar.weekdays.0`); a key
  that itself contains a dot sits in brackets. The translator never edits keys.
- **`source`** is the English text and **`target`** the translation.
- **`note`** is the code comment written above the key, if there is one. It is often the only
  context a translator gets.
- **`"status": "MISSING"`** with `target: null` means there is no translation yet. This happens
  when the locale has no block at all.
- **`"status": "MT"`** marks a machine-translated draft. The reviewer deletes the status once they
  have read the string. MT strings are never imported.

### What the import refuses

The import writes nothing at all when the file:

- leaves out a key the locale has (importing it would drop the key);
- names a key the dictionary does not have;
- still has a `MISSING` or `MT` string;
- changes a string's `{placeholders}` relative to the English source;
- has an empty target.

If the English `source` changed since the export, the import still runs but prints a warning,
so the reviewer re-checks that line.

Only the literals whose value changed are rewritten, each in the quote style it already had.
Comments, formatting and key order never move. An import with no edits is byte-identical, and
`scripts/test/i18n-pipeline.test.mjs` (`npm run test:i18n-pipeline`, part of `test:unit`) pins
that against the real dictionary.

## Terminology and the vertical overlay are not translations

- **The MARKETING vertical overlay** (`src/i18n/verticalOverlays.ts`) swaps the internship words
  for sales words, per locale. A new locale needs its overlay block too. `check:i18n` pins the
  leak count per locale (`EXPECTED_LEAKS`).
- **A tenant's own terms** ("coach" for mentor, [`docs/terminology.md`](terminology.md)) are
  data. The closed token catalogue in `src/lib/terminology.ts` has per-locale word forms, and a
  new locale needs its forms there.

## Localised content outside the dictionary

The pipeline exports the dictionary only. The following carry their own per-locale text and are
part of adding a locale by hand. `tsc` lists most of them for you: every
`Record<Locale, …>` stops compiling until it has the new key.

- `DocumentRequirement.labels`, `EvaluationCriterion.labels`: JSON `{ en, tr, de }` written by
  admins. A missing locale falls back to English at read time, so nothing breaks; the tenant
  translates its own rows.
- Tenant-authored per-locale maps (announcements, goal / message / agenda templates): these are
  filled through the machine-translation assist (`src/lib/machineTranslation.ts`, #2055), which
  marks what it wrote.
- Curated content: `src/lib/newsletterContent.ts`, `src/lib/goalTemplates.ts`,
  `src/lib/programTemplates.ts`, `src/lib/offerLetterTemplates.ts`,
  `src/lib/nextStepSuggestions.ts`, `src/lib/trustAssurance.ts`.
- Release notes: every release fragment carries `notes` in each shipped locale
  ([releases/README.md](../releases/README.md)), and the fragment check enforces it.

## Adding a locale

1. Add it to `locales` in `src/i18n/config.ts`. LTR only for now: RTL is out of scope by GTM
   decision.
2. Add a `const xx: Dict = { … }` block (start as a copy of `en`) and put it in
   `dictionaries`.
3. Run `npm run i18n:export -- --locale xx`. The block is a copy, so every target is the English
   string. Translate it (or run the marked machine pass), have it reviewed, then
   `npm run i18n:import -- i18n/exports/xx.json`.
4. Run `npx tsc --noEmit` and fill every `Record<Locale, …>` it names (the list above), the
   vertical overlay and the terminology word forms.
5. Run `npm run check:i18n` (parity, empty strings, leak ratchet) and `npm run build`, and add
   an e2e check that loads the landing page in the new locale.
6. Dates and numbers come from `Intl` through `src/lib/relativeTime.ts` (`formatDate`,
   `formatDateTime`) and `intlLocaleFor()`. Check them in the new language.
   `check:locale-dates` fails on a locale-less `toLocale*()`.

## CI gates that catch mistakes

| Gate | Catches |
|------|---------|
| `npx tsc --noEmit` | a missing key in any locale block; a `Record<Locale, …>` without the new locale |
| `npm run check:i18n` | empty / whitespace-only strings, key drift, the MARKETING leak count |
| `npm run check:i18n-scopes` | a namespace a page reads but its scope does not ship |
| `npm run check:locale-dates` | a date rendered with the browser's locale instead of the app's |
| `npm run test:i18n-pipeline` | export/import drift: the round trip is no longer a no-op |
