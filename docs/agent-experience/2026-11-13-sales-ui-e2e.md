## 2026-11-13 — rep outbox, bulk outbox and lead-pool card e2e (P5)

- **Grep the API specs before writing a UI spec, and only add the gap.** The outbox API was
  already pinned (`outbound-approval.spec.ts`: visibility, bulk API answers, admin preview and
  send), and so was the pool API (`klaviyo-connector.spec.ts`: list, claim, 409). What no spec had
  driven was the rep's side of the glass: `/sales/outbox` scoping, the select-all / bulk bar
  with its confirm dialog, the pool card's "taken" message, and navigation after a claim.
  `e2e/sales-outbox-pool-ui.spec.ts` covers those only.
- **To test a race on a client card, load the page first, then let the colleague win through
  the API.** The card still shows the stale row, so a click hits the real 409 path. Asserting
  the message and the row disappearing then tests the UI half of #419.
- **A held mail to fill the outbox needs the outbound-approval setup:** a fake SMTP server,
  `SMTP_USER` set in the spec's own process, and `sendEmail(...)` answering `'HELD'`. Copy that
  setup from `outbound-approval.spec.ts` rather than writing `OutboundDraft` rows by hand; a hand
  row has no sealed mail, so "send" would have nothing to queue.
